# 소셜 로그인과 겹치지 않는 아이디

2026-08-04 · 설계 문서 (아직 승인 전, 구현 안 함)

두 가지를 같이 푼다. 따로 풀면 두 번 뒤엎게 된다.

1. **아이디가 겹칠 수 있다.** 지금은 겹침을 막는 게 KV 위의 `get` → `put` 하나뿐인데, 그건 막을 수 없는 방식이다.
2. **소셜 로그인을 붙인다.** 붙이는 순간 아이디를 *사람이 고르는 게 아니라 시스템이 만들어야* 하므로, 1번을 안 풀면 새 아이디가 옛 아이디를 덮는다.

---

## 1. 지금 무엇이 깨져 있나

`POST /a/signup` 은 이렇게 생겼다.

```ts
const stored = await env.HISTORY.get(`u:${id}`);
if (stored !== null) return fail(409, '이미 있는 아이디다');
await env.HISTORY.put(`u:${id}`, JSON.stringify(account));   // ← 무조건 덮어쓴다
```

**Workers KV 에는 CAS 가 없고, 쓰기는 전 세계에 최대 60초에 걸쳐 퍼진다.** 그래서 `get` 이 `null` 을 돌려주는 것은 "이 아이디가 비어 있다" 는 뜻이 아니라 "이 엣지가 아직 못 들었다" 는 뜻일 수 있다. 결과:

- 같은 아이디로 두 번 가입하면 **뒤에 온 사람이 앞사람의 `{s, h, code}` 를 덮는다.**
- 앞사람은 **로그인이 안 되고**(비밀번호 해시가 남의 것이다), 그 사람의 기록은 주인 잃은 코드에 남는다.
- 아무 오류도 안 난다. 조용히 계정 하나가 사라진다.

이건 이미 `ponytail:` 로 적혀 있는, 알고 감수한 위험이다. 다만 감수한 이유("퍼즐 게임")는 **비밀번호 가입에만** 해당한다. 소셜 로그인이 붙으면 얘기가 달라진다.

### 소셜 로그인이 이걸 어떻게 악화시키나

소셜 로그인에는 사람이 타이핑하는 아이디가 없다. 그래서 시스템이 만들어야 하는데, 가장 자연스러운 후보인 **제공자의 사용자 이름**(GitHub `login`, 카카오 닉네임)은 두 가지가 다 틀렸다.

- **바뀐다.** GitHub 사용자명은 언제든 바꿀 수 있다. 바뀌면 계정을 못 찾는다.
- **겹친다.** GitHub 사용자 `sejin` 이 로그인하면 `u:sejin` 을 쓰게 되는데, 그 자리는 **이미 비밀번호로 가입한 다른 사람**의 것일 수 있다. 반대로 누군가 먼저 `sejin` 으로 가입해두면 GitHub 의 `sejin` 이 그 계정을 통째로 가져간다.

두 번째가 진짜 문제다. 경합이 아니라 **누구나 마음먹고 할 수 있는 탈취**다.

## 2. 결정

### 2.1 소셜 계정의 열쇠는 제공자가 준 불변 식별자다

사람이 고른 적도 없고 바꿀 수도 없는 값만 열쇠로 쓴다.

| 제공자 | 열쇠 | 값 |
|---|---|---|
| GitHub | `p:gh:<id>` | 계정 아이디 |
| 카카오 | `p:kk:<sub>` | 계정 아이디 |
| 네이버 | `p:nv:<id>` | 계정 아이디 |

`:` 는 `^[a-z0-9_]{3,20}$` 에 들어갈 수 없다. 그래서 **가입 경로에서는 이 키 공간에 절대 못 닿는다.** 저장소가 이미 쓰고 있는 수법이다 — `POST /h/u:sejin` 이 400 인 것과 같은 이유다.

### 2.2 소셜 계정의 이름은 서버가 만들고, `-` 를 넣는다

순위표는 줄을 이름(`name`)으로 묶는다(`updateBoard` 의 `board.find(e => e.name === name)`). 그래서 소셜 계정에도 이름이 필요하다. 이렇게 만든다.

```
gh-7f3k9q      kk-3m1z0p      nv-x82hd4
```

`ID_RE = /^[a-z0-9_]{3,20}$/` 에 **하이픈이 없다.** 그러므로 이 이름들은 비밀번호 가입으로는 **원천적으로 만들 수 없다.** 새 저장소도, 새 인덱스도, 새 검사도 필요 없다 — 글자 하나가 두 공간을 갈라놓는다.

뒤 6자는 36⁶ ≈ 22억이다. 기록 코드가 이미 같은 논리로(22자·113비트) 겹침 검사 없이 살고 있으니, 여기서도 검사가 아니라 **엔트로피가 보증**이다. 만드는 김에 `get` 을 한 번 해보고 있으면 다시 뽑되, 그건 어디까지나 덤이다(KV 로는 확답이 안 나온다).

### 2.3 보이는 이름은 닉네임이 맡는다

`gh-7f3k9q` 를 순위표에 그대로 띄우면 흉하다. 첫 로그인 때 **제공자의 표시 이름을 닉네임 초깃값으로 심는다**(GitHub `login`, 카카오 `nickname`). 닉네임은 원래 겹쳐도 되는 값이라 새 제약이 없고, 이미 `nick ?? name` 으로 그리는 길이 있으니 코드도 안 는다.

제공자가 준 이름이 `isNick` 을 통과 못 하면(빈 값, 20자 초과, 제어문자) **닉네임 없이 만든다** — 생성된 이름이 그대로 뜨고, 본인이 나중에 고치면 된다. 남이 준 문자열을 검증 없이 화면에 앉히지 않는다.

방금 넣은 `<닉네임> 탐정` 말투가 여기서 값을 한다 — 소셜로 들어온 사람도 처음부터 이름으로 불린다.

### 2.3.1 제공자가 준 식별자도 검증한다

`sub` 은 남이 준 문자열이고 그대로 **KV 키가 된다.** 형식을 못박는다.

```ts
const isSub = (v: unknown): v is string =>
  typeof v === 'string' && /^[A-Za-z0-9_-]{1,64}$/.test(v);
```

`:` 를 막는 게 핵심이다 — 안 막으면 `sub = "x:y"` 가 `p:gh:x:y` 를 만들어 키 공간의 경계가 흐려진다. GitHub 은 정수, 카카오·네이버는 base64 계열이라 셋 다 이 안에 들어온다. 통과 못 하면 로그인을 거절한다.

### 2.4 `isUserId` 를 둘로 가른다

지금 이 하나가 세 가지 다른 일을 지키고 있다.

1. 가입 입력값 검사
2. KV 키 공간 못박기
3. `getUser()` 가 localStorage 에서 읽은 값 검사

생성된 이름은 2·3 은 통과해야 하고 1 은 통과하면 **안 된다**. 그래서 나눈다.

```ts
/** 사람이 가입할 때 칠 수 있는 것 */
export const isChosenId = (v: unknown): v is string => typeof v === 'string' && /^[a-z0-9_]{3,20}$/.test(v);

/** 계정 이름이 될 수 있는 것 (고른 것 + 서버가 만든 것) */
export const isAccountName = (v: unknown): v is string =>
  isChosenId(v) || (typeof v === 'string' && /^(gh|kk|nv|go)-[a-z0-9]{6}$/.test(v));
```

여기가 이 설계에서 **버그가 날 가장 유력한 곳**이다. 두 함수를 바꿔 부르면 탈취 구멍이 그대로 열린다. 진리표 테스트를 붙인다.

| 값 | `isChosenId` | `isAccountName` |
|---|---|---|
| `sejin` | ✅ | ✅ |
| `gh-7f3k9q` | ❌ | ✅ |
| `gh_7f3k9q` | ✅ | ✅ |
| `xx-7f3k9q` | ❌ | ❌ |
| `gh-7F3K9Q` | ❌ | ❌ |
| `u:sejin` | ❌ | ❌ |

### 2.5 비밀번호 가입의 경합은 그대로 두고, 올라갈 곳만 적어둔다

KV 로는 못 고친다. 노출은 "두 사람이 60초 안에 같은 아이디를 고르면서 동시에 가입" 이고, 이 규모에서는 사실상 안 일어난다. 지금의 `ponytail:` 주석을 유지하되 **올라갈 사다리를 D1 로 못박는다** — `CREATE TABLE accounts (id TEXT PRIMARY KEY)` 에 `INSERT` 하면 겹침이 원자적으로 실패한다. 바인딩 하나만 늘고 npm 의존성은 안 는다. Durable Objects 보다 이쪽이 이 문제에 맞다(계정표는 작고, 필요한 건 직렬화가 아니라 유니크 제약이다).

**소셜 경로는 이 위험이 없다.** 열쇠를 제공자가 주므로, 같은 사람이 동시에 첫 로그인을 해도 만들어지는 두 계정 중 지는 쪽은 **기록이 하나도 없는 빈 계정**이다. 잃을 게 없다.

## 3. 어느 소셜 로그인부터인가

원래 순위(GitHub → 네이버/카카오 → Google)는 **구현 난이도와 맞다.** 두 가지만 덧붙인다.

| | 심사 | 시크릿 | 불변 식별자 | 워커 비용 | 걸리는 것 |
|---|---|---|---|---|---|
| **GitHub** | 없음 | 필요 | `id` (int64, 전역, 재사용 안 함) | ~20줄, JWT 없음 | **콜백 URL 이 하나뿐** |
| **네이버** | 사전 검수 2~3영업일 | **불필요** | 이용자 식별자 (앱별) | ~20줄 | 검수 전에는 테스터만 |
| **카카오** | 없음(기본 항목) | 필요 | `sub` (앱별) | ~25줄 | 이메일 쓰려면 비즈앱 |
| **Google** | 브랜드 인증 | 필요 | `sub` (전역) | ~25줄 | 인증 전 "미확인 앱" 경고 |

확인한 근거:

- **네이버가 유일하게 시크릿이 필요 없다.** `https://nid.naver.com/.well-known/openid-configuration` 이 `token_endpoint_auth_methods_supported: ["client_secret_post", "none"]` 을 선언한다(직접 받아 확인). PKCE S256 과 묶으면 워커에 비밀이 하나도 안 남는다. 카카오는 `["client_secret_post"]`, Google 은 `["client_secret_post", "client_secret_basic"]` 뿐이다.
- **GitHub OAuth 앱은 콜백 URL 이 하나다.** 문서에 그대로 있다 — *"OAuth apps cannot have multiple callback URLs, unlike GitHub Apps."* 로컬 개발과 배포본을 같이 등록할 수 없다. **GitHub App 으로 등록하면 10개까지** 되고 사용자 플로우와 `id` 는 똑같다. 그래서 OAuth App 이 아니라 **GitHub App** 을 만든다.
- **네이버 검수는 요청 항목을 "이용자 식별자" 하나로 줄이면 가볍다.** 휴대전화번호를 요구할 때만 사업자등록을 본다.
- **카카오는 기본 항목(`sub`·닉네임·프로필사진)에 비즈앱이 필요 없다.** 이메일·전화·생일·성별을 요구할 때만 필요하고, 우리는 아무것도 안 받는다.

### 결정: GitHub 먼저, 그다음 카카오

- **GitHub 먼저.** 심사가 없어서 오늘 만들고 오늘 붙일 수 있다. 계정 연결 설계 전체(§2)를 가장 싸게 끝까지 검증하는 길이다. 지금 이 게임을 여는 사람들도 GitHub Pages 에서 온다.
- **그다음 카카오.** 여기가 진짜 사용자다. **GitHub 로그인은 우리에게 제일 쉽지만 한국 캐주얼 플레이어에게는 제일 낯설다.** 사람을 모으는 게 목표라면 카카오가 그들이 기대하는 버튼이다. 심사도 없다.
- **네이버는 세 번째.** 시크릿 없는 플로우는 우아하지만 검수 2~3일이 걸려서 첫 번째로는 나쁘다.
- **Google 은 마지막이거나 안 한다.** 홈페이지·개인정보처리방침 URL 을 세우고 브랜드 인증을 받아야 "미확인 앱" 경고가 사라진다. 얻는 것에 비해 절차가 제일 많다.

### 두 번째 제공자를 싸게 만드는 구조

워커에 **일반 OAuth 핸들러 하나**와 제공자별 표를 둔다. 라이브러리는 안 쓴다.

```ts
type Provider = {
  authorize: string;
  token: string;
  /** 교환한 토큰으로 불변 식별자와 표시 이름을 얻는다 */
  identify: (token: string) => Promise<{ sub: string; name: string }>;
  secret?: boolean;   // 네이버는 false
};
```

GitHub 만 OIDC 가 아니라서(`api.github.com/user` REST) `identify` 가 함수여야 한다. 그 외에는 URL 세 개 차이다.

## 4. 플로우

```
브라우저 → GET  /a/oauth/gh/start
                워커가 state + PKCE verifier 를 KV 에 60초 TTL 로 저장하고 302
제공자   → GET  /a/oauth/gh/callback?code=…&state=…
                워커가 state 를 소모하고 code 를 교환 → sub 획득
                p:gh:<sub> 조회 → 있으면 그 계정, 없으면 만든다(§2.2)
         → 302 앱으로, #t=<1회용 티켓>
브라우저 → POST /a/oauth/claim {t}  → {code, nick}
```

**기록 코드를 리다이렉트 URL 에 직접 싣지 않는다.** 코드는 복구 키라 브라우저 기록에 남으면 안 된다. 대신 60초짜리 1회용 티켓(`t:<랜덤>` → 코드)을 주고 SPA 가 POST 로 바꿔간다. 열 줄쯤 더 들지만 복구 키가 URL 에 안 남는다.

`state` 는 CSRF 방어라 필수다. PKCE 는 네이버의 시크릿 없는 모드에 필요하고, 나머지에서도 켠다.

## 6. 첫 삽은 어디까지인가

이 문서는 두 가지를 다루지만 **한 번에 만드는 건 하나**다.

**1차 (이 설계의 구현 범위)**

- §2.4 `isChosenId` / `isAccountName` 분리 + 진리표 테스트
- §2.1~2.3 를 GitHub **하나만** 놓고 구현 — `p:gh:`, `gh-` 이름, 닉네임 심기
- §4 플로우 전체(state·PKCE·1회용 티켓)
- §5 파일 분리

**2차 이후 (별도 설계 없이 표만 늘리면 되게)**

- 카카오 — 제공자 표에 한 줄. 실제 사용자가 여기 있다
- 네이버 — 검수 신청을 먼저 넣어두고, 승인 나면 붙인다
- D1 로 비밀번호 가입 경합 닫기 (§2.5) — 필요해지면

1차가 끝나면 §2 의 겹침 문제는 **전부 닫힌다.** 2차는 제공자를 늘리는 일이지 설계를 바꾸는 일이 아니다.

## 8. 사람이 해야 하는 것

코드로 못 하는 부분이다.

1. GitHub → Settings → Developer settings → **GitHub Apps** 에서 앱 등록 (OAuth App 아님 — 콜백 URL 하나 제한 때문에)
2. 콜백 URL 두 개: `http://127.0.0.1:5493/…` 와 배포 주소
3. `cd worker && npx wrangler secret put GH_CLIENT_SECRET`
4. `GH_CLIENT_ID` 는 `wrangler.toml` 의 `[vars]` 에 (비밀이 아니다)

## 9. 안 하기로 한 것

- **아이디·비밀번호 로그인을 없애지 않는다.** 소셜 계정이 없는 사람이 있고, 기록 코드가 이미 복구 수단이다.
- **계정 병합(같은 사람의 GitHub + 카카오를 하나로)을 안 만든다.** 필요해지기 전에는 만들 이유가 없고, 병합은 되돌리기 어렵다. 지금은 **제공자마다 계정 하나**다.
- **이메일을 안 받는다.** 안 받으면 카카오 비즈앱도, 네이버 사업자 확인도, 개인정보 처리 부담도 다 사라진다.
- **닉네임 겹침을 여전히 안 막는다.** 이 설계는 *아이디*를 갈라놓을 뿐, 닉네임은 원래 겹쳐도 되는 값이다.
